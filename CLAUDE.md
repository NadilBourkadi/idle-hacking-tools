# Idle Hacking — research, strategy and tooling workspace

Long-running analysis workspace for the browser game **Idle Hacking** (single-player campaign). Migrated from a ChatGPT Project on 2026-07-22; the raw handover is preserved in the initial git commit. Three kinds of work happen here: loadout/crafting strategy analysis, game-mechanics research, and development of the passive capture userscript.

## Source-of-truth order

1. The latest capture in `data/captures/` (query via `scripts/ih.py`).
2. `docs/current-state.md` (interpretation) and `docs/decision-log.md`.
3. `docs/mechanics.md`, `docs/crafting.md`, `docs/static-analysis-2026-07-22.md`.
4. Older schema-4/3 exports (`data/loadouts/`) and historical combat logs (`data/combat/`).

The profiler is unlimited at a 5 s cooldown (~72,000 simulated fights/hour, free) and returns `enemy_stats` with every logged fight, so it is the first instrument here that can measure a combat formula directly instead of inferring a weight.
- `docs/game-client-internals.md` — how the game client stores state (bindings, item schema, WS protocol); basis for full-state capture. Game JS reference copies: `vendor/game-js/` (git-ignored).
- `data/captures/` — full-state captures (authoritative, auto-routed by the hub); `data/combat-stream/` — daily JSONL ledger of deduped fights/deaths/stat-changes from the userscript auto-stream (hub-extracted, raw stream not stored); `data/incoming/` — non-capture staging; legacy exports in `data/loadouts/` and `data/combat/` (see `data/README.md`).
- **Inventory is not a keep-by-default store: anything NOT `decompile_locked` is regularly decompiled and lost** (player's standing operating model, 7 Aug 2026). The lock flag is therefore the only thing between a craft base and deletion, and drift in it is a silent irreversible loss — `ih.py locks` prints the daily **delta** (lock these, unlock-and-decompile those) and `ih.py audit` flags both directions. Value is the **weaker** of raw Δ and Δ-ex-suspect so no lock verdict rests on a flagged weight; the **revert path of a hot A/B is held by name** via the experiment's `revert_item`. **Hold depth is ONE base per slot** (`ihlib.KEEP_DEPTH_PER_SLOT`), and that number is measured, not taste: band-clearing bases arrive at **0.92/day**, the median base is **crafted 1.2 days after dropping** (max ever 4.5, n=8), and **holding is not free — inventory was 94/102 with slots priced at 10 hackcoin (~83B credit-equivalents)**. The first sweep recommended holding 13; the player challenged it as excessive and was right, because none of those three numbers had been looked up. A deeper queue is never drawn down before it is superseded. The first sweep found the lock set almost exactly inverted against value (17 of 18 locked items not worth holding, 13 band-clearing bases unlocked) because locks were set by hand over weeks and never revisited.
- `data/sim-runs/` — daily JSONL ledger of Hacking Simulator runs (hub-deduped by result hash); query with `ih.py sims`.
- `data/predictions.jsonl` — prediction ledger (projected vs realized per craft, tagged by planner era); scored by `ih.py calibration`.
- `scripts/ih.py` + `scripts/ihlib.py` — capture query CLI and analysis library (slot map, scaling law, cost model, archive-wide tier ladders, craft-contract simulator and measured fight cadence as code).
- `tools/item-loadout-capture.user.js` — the read-only Tampermonkey capture script (version in the `@version` header; bump on every change).
- `scripts/capture-hub.py` — localhost:8123 hub (systemd user service `idle-hacking-capture-hub`): serves the userscript to Tampermonkey and routes incoming exports by schema.

## Working with the data — query-first

**Run `ih.py assumptions` before any verdict that rests on a weight or a threshold.** It is the provenance register for every tunable constant — `measured` / `asserted` / `inherited` / `supplied`, when each was last validated, and a live re-check for the ones that can self-validate. **Every defect ever found in this workspace has been an `asserted` or `inherited` row in that table** (T3 tier cap, zone transition cost, "attack speed → fights per hour", `Corrupt = 0.6`, "credits ≈ unlimited", `floor = 8`). Only 2 of the 27 constants remain untested (`MaxHP` — bracketed live from both signs 31 Jul–1 Aug but still unfitted, and the `AtkSpd` rationale; `Regen`'s magnitude was measured 6 Aug 2026 on the CI/CD pair at 0.119 streaks/item-flat point) — treat a number from those as a hypothesis, and say so in the advisory rather than quoting its output as fact. New tunable constants must be added to `ihlib.assumptions()` in the same change that introduces them.

**Use `python3 scripts/ih.py <cmd>` for all capture queries; never parse capture JSON ad hoc.** Full-state captures land in `data/captures/` automatically (hub routes by schema); latest = lexicographically last. Commands: `audit`, `captures`, `loadout`, `item <query>`, `candidates [--slot s]`, `compare <a> <b>`, `diff [old new]`, `stats`, `history <query>`, `potential [--slot s] [--cap N]`, `homelab`, `hardware`, `ab`, `sims`, `locks`. For bespoke analysis, import `scripts/ihlib.py` — it encodes the slot mapping, scaling law, cost model, stat-composition families, hardware cost curve/planner and empirical tier ladders so they are never re-derived.

**Write every contract with `ih.py contract --deepen`, and aim deeper than `plan_craft` proposes.** `plan_craft` stops when the next step's expected Stability exceeds the remaining budget, which maximises P(all phases complete) — a vanity metric. Tier value compounds while attempt cost grows only linearly, and an over-committed plan that runs out of Stability just stops, leaving a shallower craft that is still an upgrade and that you need not equip. Downside bounded, upside not. Measured on the 29 Jul Daemon: the contracted plan scored mean +15.6 / p10 +7.8, deepening the single highest-value affix by one tier scored **mean +21.3 / p10 +7.1 with an identical worst case** — +37% expected value for 0.7 of p10. The player beat the contract this way twice before it was modelled, which is the general lesson: **a repeated, successful deviation from a recommendation is a defect report about the recommendation.**

**Judge a close craft by simulating the contract, not by discounting it.** `ih.py contract <item> [--phase 'of Haste:4' ...] [--order]` returns the outcome distribution — mean/median/p10/p90, `P(Δ > UPGRADE_BAND)`, `P(all phases complete)`. The old practice of taking `potential`'s ceiling and subtracting a flat ~5 points said the Aegisbound Driver was +4.1 (a sidegrade, held); simulation said **P(Δ > +5) = 90.8%**, it was approved, and it realized **+16.7**. A flat discount cannot see that phases are **non-separable** (Stability spent cuts Compile, which multiplies every affix, so each phase alone is worth far less than in combination), nor that the downside is bounded and optional — a bad craft simply is not equipped. **Phase order is not cosmetic**: an expensive low-probability step belongs last, where it absorbs leftover Stability instead of starving the cheap phases (90.8% vs 81.0% on identical phases). Use `--order` to search.

**Run `ih.py audit` first, every time, before any optimization.** It sweeps for things silently costing progress — idle build slots and empty queue places, hardware tracks whose multiplicand is zero, unspent or shop-locked chips/hackcoin, finished crafts still unequipped, and stale lazy panels. Every check exists because a real instance was missed by going straight to modelling. The biggest wins of 27 Jul 2026 all came from reading neglected fields, not from better models.

- `ih.py potential` plans as deep as the Stability budget allows (to T1, the game max). It used to stop at T3, which excluded the two best purchases on the ladder — gain per expected Stability point *rises* all the way down and peaks at T3→T2. Pass `--cap 3` only to reproduce pre-27-Jul-2026 numbers.
- Reusable primitives in `ihlib`, verified against live captures: `composed_stat_total` (reproduces every stat exactly; use it for "what if I add X pool/flat" instead of hand arithmetic), `hardware_cost_curve` / `hardware_cumulative` / `hardware_plan` (chip cost law and equal-marginal-value allocation; the curve self-validates to ~1.5% against the game's own reset refund), `panel_freshness` / `stale_panels`.

**Candidate judgements use post-craft ceilings, never current rolls.** Equipped items are at 0 Stability (final); inventory items carry 25–30 Stability of Version-Upgrade headroom, so `compare`/`candidates` output systematically understates them. `ih.py potential` projects realistic ceilings (empirical tier ladders, budget-limited tier depth, Compile floor) and prints a **`from:` decomposition** of every Δ — read it, because a scalar hides which weight is carrying the verdict, and it flags any Δ leaning on a known-bad weight.

**The "~5-point contract-conservatism discount" is retired — it has the wrong sign.** `ih.py calibration` scores the prediction ledger (`data/predictions.jsonl`) and **6 of 9 crafts realized ABOVE projection**; bias is **+15.9** under the uncapped planner and **+18.6** under uncapped+archive ladders. Subtracting 5 from a projection that already under-shoots by ~16 is how the Aegisbound Driver got held at "+4.1" before realizing +16.7. Judge close crafts with `ih.py contract` (which returns P(Δ>+5) and p10 directly), never by adjusting a point estimate. **Record every approved craft with `ih.py calibration --record` at contract time and fill `--realized` after** — there are currently *zero* graded crafts under the present planner, so the next two are calibration runs and their full distributions must be logged.

- Captures are ~1 MB each. **Never read one whole** — `ih.py` or targeted `ihlib` scripts only.
- `statsBreakdown`/`extendedStats`/`combatLog`/`recentLossStreaks`/`homelabInfo` are lazy — captured only if the corresponding game panel was opened that session (`ih.py captures` shows what each capture contains).
- Anything in `data/incoming/` is non-capture output needing manual triage. Legacy schema-4/3 exports and combat logs live in `data/loadouts/` and `data/combat/` (one `DUPLICATE-` file there counts once; field semantics: `docs/data-dictionary.md`).
- Data files are immutable once written; new capture > editing an old one.

## Never defer a known defect (highest-priority rule in this file)

**When you discover something is wrong, fix it in the same session you discover it. There is no "later".** This has been the single most damaging failure mode in this workspace, it has recurred in several disguises, and every instance looked reasonable at the time.

- On 29 Jul 2026 `CRAFT_WEIGHTS_FLAT["Barrier"]` was measured at ~5x its applied value and **deliberately left unchanged**, with the written justification that re-fitting "moves live verdicts, so it belongs in its own change". Every candidate ranking produced for the rest of that session was computed from a number already known to be false — including a craft verdict that was acted on. It surfaced only because the player asked an unrelated mechanical question hours later.
- `CRAFT_WEIGHTS_PCT["Acc"]` sat at an asserted `1.0` for two days after being flagged as "probably far too high", with `potential` printing "ex-suspect" footnotes instead of the weight being fixed. Measured value: **0.14**. Everything Accuracy-carrying was mis-ranked in the meantime.

**The reasoning that produces this failure is always plausible**, which is why it needs a hard rule rather than judgement: *"it deserves its own change"*, *"it would move live verdicts"*, *"an A/B is mid-flight"*, *"resolve it with the Software Profiler later"*, *"flag it and move on"*. All of these are ways of shipping advice you already know is wrong. **Note the asymmetry that makes them wrong: leaving a known-bad value in place also moves verdicts — away from the truth — and does it invisibly, with no flag on the output.** A fix is visible and reviewable; a deferral is neither.

Concretely:

- **Fix it now.** A weight, a doc line, a mis-scoped filter, a wrong field description, a broken accessor — correct it in the same change, then re-run whatever the change invalidates and re-state any verdict that moves. Say plainly in the reply that a number changed and why.
- **A deferral is only legitimate when the fix is blocked on data that does not exist yet** — not on effort, tidiness, or comparability. Then it MUST be entered in `ihlib.PENDING_REFITS` with an `unblock` naming the specific observation that resolves it. `ih.py audit` lists those rows **first**, and `potential`/`contract` print a banner while any exist, because numbers computed from a known-wrong constant must never look clean.
- **Never let an in-flight A/B block a fix.** Comparability is worth less than correctness. Re-baseline the test, or record the change as a segment boundary — both are cheap, and both are what `ih.py ab` already supports.
- **This outranks the output format, the session's plan, and the user's immediate question.** Fixing the defect *is* the work.

## Code changes — review before the session ends

**When a session makes significant changes to `scripts/`, `tools/` or `tests/`, run the `/code-review` skill before wrapping up.** "Significant" means anything beyond a one-line constant or a comment: a new command, a new `ihlib` function, a changed signature, a fixed defect, a new audit check. Run it *after* the change is complete and the tests pass, not instead of them — the suite proves the code runs, the review is what catches the class of thing this workspace keeps rediscovering by accident.

The case for it is the workspace's own history: every defect here has been found by a human question or a coincidence, never by the code being re-read on purpose. The 7 Aug affix-name collision was caught only because a contract mean exceeded a planner ceiling and someone noticed the impossibility; the homelab ETA was wrong by 3.125x for as long as the panel existed; `decompile_locked` sat unread in the schema for three weeks. Each was cheap to find once looked at, and expensive while it stood — the collision was inflating a live craft verdict, and the lock drift was one click from irreversible loss.

- Run it on the session's diff, not the whole tree.
- **Fix what it finds in the same session** — the anti-deferral rule above governs review findings exactly as it governs weights. A review whose findings are deferred is worse than no review, because it produces a written record that the problem was known.
- Report the findings and what was done about them; if a finding is declined, say why in the reply.

## Git workflow — branch, atomic commits, PR, merge on the player's word

Adopted 7 Aug 2026 at the player's request. The repo is public under Nadil's name, so history is part of the deliverable.

- **Never commit directly to `main`.** Branch per session or per theme: `fix/<thing>`, `feat/<thing>`, `chore/<thing>`.
- **Commit when a unit of work is coherent and green** — a defect fixed with its regression test, a command added with its wiring, a doc set updated together. Not per file, not per hour, and never a single "session dump" commit. If a change would need the word "and" twice to describe, it is more than one commit.
- **Each commit must stand alone: the suite passes at every commit**, not just at the tip. A commit that only works with the next one is not atomic — rebase them together instead.
- **Rebase into a readable story before pushing.** Reorder so mechanical/refactor commits precede behavioural ones, squash fixups, and drop noise. The history should read as how the work *should* have been done, not how it actually stumbled.
- **Message format:** `<type>(<scope>): <imperative summary>` then a body explaining **why**, and — for anything found by review, audit, or accident — *how it was found*, because that provenance is what this workspace keeps needing later. Reference the defect's symptom, not just its fix.
- **Never add a `Co-Authored-By: Claude` trailer** (see `.claude/settings.json`).
- **Run `make ci` before every push, and treat it as the gate.** It runs exactly what `.github/workflows/ci.yml` runs — `ruff check`, the unittest suite, and the fresh-clone import. Running `python -m unittest` alone is NOT sufficient and has let a red PR through twice: ruff was never run locally, and a test that read a live capture passed here (146 captures on disk) while failing in CI, where `data/` is git-ignored so a clone has none.
- **The suite is data-isolated by construction, not by discipline.** `IH_DATA_DIR` overrides `ihlib.DATA_ROOT`, and the tests point it at an empty temp tree so no test can see the working tree's captures; `DataIsolationTest` asserts it. Build synthetic captures in tests — never call `load_capture()`. Note the isolation is set in **both** `tests/__init__.py` and the top of `test_ihlib.py` on purpose: `unittest discover tests` (what CI runs) makes `tests/` the top level and never imports the package `__init__`, so the `__init__`-only version silently did not apply.
- **After pushing, poll the run to completion and fix failures without being asked** — `gh run list --branch <b> --limit 1` then `gh run view <id> --log-failed`. A red PR is not a notification for the player to action; it is unfinished work. Fix, re-run `ci-local.sh`, push again, and only report once it is green. **Note a failing job can mask later ones**: `ruff` failing means the tests never ran, so re-check the full pipeline after each fix rather than assuming one failure was the only one.
- **Push the branch and open a PR with `gh`**, with a body that leads on the decision-relevant changes (moved numbers, changed verdicts, new commands) and separates *behavioural* from *documentation* changes. Then stop.
- **Do not merge without the player's explicit go-ahead.** After approval, merge with the `gh` CLI. Delete the branch after merge.
- **`data/` is git-ignored** — captures and ledgers are never committed. Check `git status` before every commit rather than assuming.

## Analysis rules

- **Every recommendation resolves to a specific action.** Never write a bare imperative with no object — "refill the homelab", "spend the chips", "buy some upgrades". Name the upgrade/item, target level, cost, duration and **always the UI section it sits under** (homelab upgrades live beneath an install — "Virtual Desktops [Command Workstation]", never just "Virtual Desktops"). A name without its panel still means hunting. `ih.py audit` and `ih.py homelab` print a QUEUE block naming the exact jobs (`ihlib.homelab_fill_suggestions`), ranked by **points per slot-hour** — see the homelab throughput rule below.
- **Progression first; measurement second.** The point of this workspace is to make the player progress faster, not to run clean experiments. Recommend every worthwhile action in the same session; never stagger independently-good actions to keep their effects attributable, never gate progress behind collecting a baseline, and never freeze a queue to protect a test. Sequence two actions only when one changes the *correct choice* for the other. Confounded windows are acceptable — state that the period measures a bundle and move on. A/B discipline still governs how a test is *read* (see `docs/crafting.md` §14), never whether progress waits for one.
- **If one unknown fact would flip the recommendation, it is a blocker — resolve it or branch the advice on it.** Never write the confident version and append the unknown as a closing caveat. On 28 Jul 2026 a whole strategy ("defer the Hacking Simulator, switch the homelab to credit-efficient jobs") rested on credits being a depleting stock; the advisory *itself* noted that the unexplained +22.25B windfall of 22 Jul "decides whether the Hacking Simulator is ever affordable" — correctly identifying the unknown as decision-critical, then demoting it to a footnote. Hackcoin converts to credits at ~8.33B each; one question would have replaced hours of analysis. Corollary: **a stock-and-flow model of any currency is incomplete until the conversion graph is checked** — what converts into it, what it converts into, at what rate.
- **Never recommend a spend without its denominator, and measure the rate before recommending, not when challenged.** "Spend 133,530 chips" is not an action; "133,530 chips = 24h of income = 98% of stock" is a decision — and on 28 Jul writing the denominator down changed both the allocation (all-ECC, not a split) and the size. Also check whether the spend is **recoverable** (hardware chips refund ~fully at the monthly reset). And do not hedge against a risk you have not sized: half a chip budget was allocated to offset a craft's −6% Defense before one query showed Defense was still above every reading from before that day. Same family as the bare-imperative rule above.
- **Before a quantity enters a verdict, check whether anything has ever measured it — and if nothing has, check the archive for natural variation before concluding it is unmeasurable.** The capture archive is a longitudinal dataset and most weights have a free natural experiment sitting in it. `CRAFT_WEIGHTS_FLAT["Corrupt"]` was fitted on one fight at 12 points; Corruption had since run 12.06 → 23.11 → 24.84 → 16.20 with the ledger recording throughout, which was enough to show the stated rationale was ~2× off and the response non-linear. Nobody looked for six days. Segment by the stat's own change-points, match on streak band, and normalize against a co-scaling quantity (corruption as a share of direct damage) so player growth does not masquerade as effect. "Attack speed → more fights per hour" was never measured, was asserted, and then propagated through four sessions of advice, priced into two craft verdicts and written into an A/B keep rule. Fight cadence is a **fixed real-time tick** (~4.65 s in the current era — it era-steps, see `ih.py cadence` and `mechanics.md` §14): a +9.9% Attack Speed equip moved it 0%. The ledger could have falsified it at any point. This is not a model used outside its regime — it is a number nobody ever looked up. Where a quantity is measurable from the ledger, measure it before it becomes an argument.
- **A model fitted on *currently-owned* state rots when the inventory turns over.** Tier ladders were fitted per-capture, so decompiling a +1.7 sidegrade deleted the only `suffix_adaptive_shell` T7 observation owned and moved a live verdict **+9.0 → +4.6 with no game state changed at all**. Affix ranges are game constants, so `ihlib.tier_ladders_archive()` now unions every capture (150 → 582 observations). Prefer archive-wide fits wherever the underlying quantity is a constant.
- **An A/B keep rule may gate on the outcome and on contamination checks — never on the mechanism you guessed.** Being right about the effect and wrong about why is the normal case. The `driver-ab-2026-07-27` rule made rounds/fight a necessary condition alongside death streak, so an item delivering +5.7 streaks by another route would have scored REVERT. Amend a rule only for impossibility (a metric that is constant cannot move), never after seeing a favourable result; when a rule turns out mis-specified mid-flight, record the mis-specification in writing **before** the readout and let the primary outcome govern.
- **State the regime a model was fitted in, and re-validate before using it outside that regime.** This failed three times on 27 July 2026 alone: the craft planner's T3 tier cap (never tested — it excluded the two best steps on the ladder); the zone transition cost (fitted on a handful of high-streak fights in one zone, wrong by 4.5× when applied across zones); and `hardware_plan` (validated only at a ~1.08M-chip full-reset budget, returned a 108K-chip plan against a 37K balance). Each looked reasonable in output, which is exactly why none was caught. Prefer models that **self-validate against a game-provided ground truth** — `hardware_cost_curve` checks its whole-build total against the game's own reset refund and would flag its own drift. Where that is impossible, exercise the model at both ends of the range before trusting it.
- **Declare the cohort before you compute anything from it.** Any era/segment filter is a regime declaration, so print its own boundaries first — `ihlib.cohort_summary(rows)` does this and warns when `max_hp` spans a gear change. On 29 Jul 2026 a post-craft cohort was selected by `17000 < max_hp < 18000` with no date bound; the 28 Jul loadout sat at max_hp 17,345–17,374, so a full day of pre-craft fights was pooled in. Two constants were "refined" from it, published, and withdrawn within the hour. One line of boundary-printing would have caught it.
- **A log field's meaning is a hypothesis until it is shown to vary with the thing it supposedly measures.** `pcd`/`ecd` were documented backwards for a week and used that way in analysis; the giveaway was that `pcd` is *flat* across all nine enemy classes, which no measure of incoming damage could be. Before a field enters an argument, run the discriminant check: find something it must correlate with and confirm it does.
- **Before concluding from a pooled mean, segment by the natural categorical and look for bimodality.** "Net drain is negative in every streak band" was true and deeply misleading: three of nine enemy classes were strongly positive and caused 100% of deaths. Segment by enemy class, zone, item era — whichever grouping the game itself uses.
- **A scalar ranking cannot audit the weights it is built from.** Every weight defect found here was found by testing a *mechanism* against the ledger, never by looking at `potential` output — which renders wrong weights as confident scores. Periodically test the top-contributing weights directly, and treat any question about how a stat works as higher priority than any ranking that uses it.
- **Audit before you model.** Anomalies in neglected fields beat optimization of well-trodden ones. Run `ih.py audit`, then read what it flags, then optimize. If you find an anomaly the audit missed, add the check — that is how the sweep stays useful.
- **Before an irreversible or once-a-month action, enumerate the state it touches and check every field it will write, not just the ones it reads.** A field that is empty now may be a post-condition field. `locked_resources` read as all-zero before the 27 Jul hardware reset, so it was treated as inert; the reset filled it, and the refunded hackcoin turned out to be permanently shop-bound — invalidating a claim already given to the player. When a field's meaning under the action is unclear, say so before recommending it.
- **Check accessibility before recommending any game system.** Homelab installs/upgrades, zones and crafting operations carry gates in the capture (`unlock_level` vs current homelab level, required install present/absent, zone `min_level`). Anything not currently reachable must be labelled with its gate ("unlocks at homelab 9"); gated upgrades may be entirely invisible in the game UI, so never assume the player has seen them. Always use display `name` fields from the capture's definitions, not internal slugs.
- **Hackcoin is the only scarce currency; credits are bought with it.** The player sells hackcoin for credits at **~8.33B credits per hackcoin** (`ihlib.HACKCOIN_CREDIT_RATE`, 28 Jul 2026). Price every decision in **hackcoin-equivalents** (`ihlib.hackcoin_equivalent`), never in credits: the Hacking Simulator's 5B credits is 0.60 hc against its 3 hc gate, so the hackcoin line item is 5× the credit one. Consequences: spend credits freely, never stagger or defer an action to bank them, and rank purchases by hackcoin cost. A 28-hackcoin balance is a ~233B credit budget — reading it as a 5.7B credit balance produced exactly one wrong recommendation (deferring the Hacking Simulator, 28 Jul 2026). Basic resources are purchasable at ~2 credits/unit, so on-hand gathering resources are never a schedule gate. **Hackcoin comes from the daily contract board** (1-5 hc per contract plus a board-clear bonus; daily UTC reset — the ACTIVE contract carries through reset and runs to completion, only unstarted contracts and the clear bonus are replaced (player-observed 6 Aug 2026, `mechanics.md` §20); `ih.py audit` prices the board), which makes contract throughput the real economic lever.

- Treat the newest structured export as the source of truth; ask for a fresh complete export when a decision depends on the current whole loadout.
- Separate verified facts, working models and unknowns. Never invent formulas or mechanics.
- Evaluate candidates as crafting bases and as parts of the whole loadout — never on Item Level alone. Follow the output contract in `docs/crafting.md` §10 (forced Augment side, Continue/Conditional/Abort outcomes, ordered tier targets, attempt caps, Stability floor, Compile timing, post-craft test).
- Long-streak loss analysis must separate accumulated attrition from final-matchup strength. Diagnose in order: attrition vs matchup → hit reliability → outgoing damage → incoming damage/burst → which one or two stats would change the result → cheapest slot to obtain them.
- Inspect start/max/end HP, streak, rounds, hits, miss events, crits, direct damage, `prg`, barrier, thorns/corruption and enemy stats.

- **Homelab build throughput is a FIXED pool split evenly across active jobs — slots never add rate** (`mechanics.md` §15, verified against the capture to three decimals; the Build Scheduler says so in its own description: "splits progress, doesn't speed up building"). Consequences, all reversing earlier guidance: rank jobs by **points per slot-hour**, because ticks are the scarce resource; an empty slot costs **nothing** while one job is running, so "4 slots sat empty 23-27 Jul" was never the loss it was written up as; the only state that loses points is **nothing active AND nothing queued**, which `audit` now flags as `IDLE` (free slots report as `COVERAGE` with hours buffered). To reach one specific target soonest — an install gate — run it with **as few concurrent jobs as possible** and state the point cost.
